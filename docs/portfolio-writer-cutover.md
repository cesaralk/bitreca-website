# Writer cutover and recovery checklist

## Solo owner policy: `solo-operator-v1` (local implementation, not activated)

This explicit policy provides owner accountability, **not independent second-person
oversight**. It preserves writer-drain requirements, P-256 verification, immutable
ownership, uncertainty blockers, cleanup manifests/receipts and separate finalization.
The independent procedure below remains valid for `independent-v1`; do not relabel
its version-1 reports or use its independent-audit acknowledgement for solo evidence.

Migration `0014_add_solo_operator_authorization.sql` defaults to independent mode,
generation zero, no enrollments or revocations. It does not raise the writer protocol
or enable any deletion control. Solo enrollment records policy UUID, increasing
generation, named operator, public-key SPKI SHA-256, scope, code-artifact SHA-256 and
enrollment time. Enrollment/history/revocation records are immutable; generation
cannot decrease or return to independent mode. Rotation/revocation increments the
runtime revision and disables cleanup/finalization. Existing independent evidence is
retained but cannot authorize solo births or deletion. Origins from an older policy
generation remain blocked; rotation does not silently migrate them.

Trusted configuration must pin `PORTFOLIO_AUTHORIZATION_POLICY=solo-operator-v1`,
`PORTFOLIO_AUTHORIZATION_POLICY_ID`, `PORTFOLIO_AUTHORIZATION_GENERATION`,
`PORTFOLIO_OPERATOR_ID`, `PORTFOLIO_OPERATOR_KEY_ID` (SPKI fingerprint), and
`PORTFOLIO_DEPLOYMENT_SHA256`, alongside the existing public-key/resource pins.
The database enrollment and deployment pins must agree. The signed version-2
payload uses the canonical field order emitted by `canonicalReport` in
`scripts/portfolio-evidence.mjs`: version, id, authorization_policy, policy_id,
policy_generation, operator_id, operator_key_id, deployment_verified_at,
writers_fenced_at, writers_settled_at, storage_scope, writer_protocol,
deployment_sha256, evidence_sha256, legacy_writers_settled, verified_at.
Times are integer UTC seconds: enrollment <= deployment verification <= fencing
<= actual settlement <= signing <= server time. All statements need real supporting
records. Empty D1/R2, owner approval, waiting, and successful tests prove no drain.

### Offline enrollment and signing (no keys generated by these tools)

The owner obtains and protects a dedicated P-256 key offline. Keep its PKCS#8 PEM
outside Git, packages, CI and deployment automation, on an encrypted offline volume
with owner-only access; retain an encrypted offline recovery copy. The CLI reads
PEM locally; it does not manage hardware tokens or passphrases. Never put private
material or passphrases in command arguments, environment pins or logs. Export only
PUBLIC PEM for pinning, compare its fingerprint directly on the offline signing
machine, and archive enrollment/generation separately from D1. Losing both the
signing key and recovery copy means deletion stays blocked, not bypassed.

`code-artifacts.json` must identify the reviewed **main and hosting JavaScript
SHA-256 digests**, including their exact bytes. Hash that file as the deployment
digest; exclude configuration containing that same digest to avoid a circular hash.
Archive the complete configuration/migration/package hashes and live version/traffic
verification separately inside the settlement-audit evidence. Runtime cannot attest
its own deployed bytes: actual provider-side comparison is still required.

The following are local-only templates. Substitute reviewed identities and real
timestamps; do not use example/synthetic reports as operational evidence:

```powershell
node scripts/portfolio-evidence.mjs enroll-solo --public-key <outside-repo-public.pem> --scope <exact-sandbox-scope> --deployment <code-artifacts.json> --policy-id <new-UUIDv4> --generation <next-integer> --operator <owner-ID> --enrolled-at <actual-UTC-seconds> --out <outside-repo-enrollment.json>
```

Review its `enrollmentSQL` and `environment` output. Extract only its `authorization`
object into an independently retained `owner-authorization.json`; this is a separate
trusted input, never inferred from the report. Confirm actual enrolled state before
signing. On the offline operator machine:

```powershell
node scripts/portfolio-evidence.mjs sign --report <actual-v2-report.json> --private-key <outside-repo-owner.pem> --scope <exact-sandbox-scope> --deployment <code-artifacts.json> --audit <actual-settlement-evidence> --authorization <owner-authorization.json> --acknowledge-owner-responsibility --acknowledge-writer-settlement-evidence --out <new-signed-evidence.json>
node scripts/portfolio-evidence.mjs verify --evidence <new-signed-evidence.json> --public-key <outside-repo-public.pem> --expected-signer <reviewed-SPKI-SHA256> --scope <exact-sandbox-scope> --deployment <code-artifacts.json> --audit <actual-settlement-evidence> --authorization <owner-authorization.json>
```

The flags acknowledge responsibility; they do not establish settlement. Keep the
signed envelope, exact hashed artifacts and append-only generation/revocation log
in immutable/versioned storage outside D1 and deployment credentials. Repository
SQL immutability does not stop an account administrator dropping triggers or
restoring a snapshot. Restrict deploy/D1/R2 credentials, remove legacy writer access,
forbid untracked rollback, and retain provider audit records. Code cannot enforce
these Cloudflare account controls or remove the owner's ultimate account authority.

## Existing independent-policy procedure

Nothing in this procedure has been executed against Cloudflare. The checked-in
configuration keeps requests, execution, finalization, evidence import, and Cron off.

1. Inventory the deployed main/hosting Workers, routes, versions, traffic splits,
   all other R2 credentials, and rollback targets. Database policy alone cannot
   stop an old HTML handler that directly PUTs to an existing key.
2. Create independently isolated staging D1 and R2 resources and restricted
   credentials. Review actual binding IDs; a name containing "preview" is not proof.
   Never run remote development with the production configuration.
3. Back up metadata and establish object recovery/version retention BEFORE enabling
   destructive features. A D1 backup cannot recover deleted R2 bytes.
4. With separate authorization, apply pending migrations in order (0012 then
   0013 when local 0001–0011 are verified). Production history must be inspected
   separately. Do not assume production matches local.
   A newly created empty STAGING database instead needs all 0001–0013. Review the
   0006 short-pattern D1 correction and the exact-target commands in
   [portfolio-staging-release-checklist.md](portfolio-staging-release-checklist.md).
5. Deploy the reviewed tracking-capable code with ALL deletion flags off. Both
   folder and HTML handlers register ownership/writer identity before each PUT,
   await every issued write, stop local issuance before closure, and fence activation.
6. Stop mutation ingress, remove all legacy deployments/traffic splits, and prove
   every legacy request and external writer has settled. A timeout is not proof.
   Preserve incident/request evidence. If settlement cannot be proven, keep affected
   storage blocked. Never edit an uncertain writer to closed just to unblock deletion.
7. Only after independent review, separately authorize raising the existing writer
   minimum to 1. It is monotonic. Old allocation/activation SQL will fail closed,
   but an already issued R2 PUT cannot be cancelled by this change.
8. Independently audit the exact deployment artifact and storage scope, then use
   the offline evidence tooling. A signature attests the auditor's findings; it
   does not discover facts or replace a drain investigation. Pin the verifier's
   public key from a separate trusted channel, not from the signed package itself.
9. Import the reviewed evidence with deletion execution still off. Only portfolios
   created AFTER this verified epoch and gate can be automatically attested. Earlier
   portfolios, even those with UUID prefixes, need separate legacy reconciliation.
10. Test new creation, both upload types, conflicts, unpublish, marking, resumable
    cleanup, and finalization in the isolated staging resources under a separate
    authorization. Inspect cost/runtime limits and every retained receipt.

## Interrupted deployment or uncertain state

Leave execution off. An open writer may be active or an interrupted checkpoint;
an uncertain writer may have committed a remote write. Neither can be settled by
age. Collect original request/operation evidence or keep its allocations blocked.
Retrying a website upload uses a NEW prefix; it never rewrites ownership history.
Do not roll back to an untracked Worker after the epoch. Roll forward to a reviewed
compatible version, or stop mutations and begin a new independent audit.

Disable environment flags and increment/disable the D1 runtime authorization to
stop additional cleanup calls. An already issued DELETE may still settle; its
immutable manifest is replay-safe and its receipts remain durable. Never delete
manifests or reset generation counters during recovery.
